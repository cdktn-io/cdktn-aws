# M8 — the migration, TypeScript

The record of one slice: `@cdktn/provider-aws` consumers get a tool that moves them to
`@cdktn/aws`, and the repository gets its first end-to-end proof that the two libraries synthesise
the same terraform. Taken 2026-09-02, against `terraform-provider-aws` 6.62.0. No version bump.

Go is the next slice; Python later. There is no 0.1.x migration path and never will be — 0.1.x was
a PoC alpha with no consumers, and the library a consumer is actually holding is the classic
per-resource one.

## Three deliverables

**A — the nested section of the rename map.** `naming-map.json` carried one row per generated
class, which is the smaller half of what a consumer holds: `S3BucketCorsRule`, its
OutputReference/List/Map classes and its two mapper functions are all nested types. Each entry now
carries `nested: { "<terraform path>": { className, classic } }`, one row per struct, and the file
publishes the fixed suffix rules (`nestedSuffixRules`) that derive the other five spellings on both
sides. `mapperPrefix` appears only where the mappers are not prefixed with the class name — the five
`s3`/`waf` entries carrying the `Mapper` disambiguator (three in `s3`, two in `waf`, between them
resolving the 21 duplicate exports `naming.ts` describes). 9,856 nested rows; 866 KB → 3.0 MB, well
inside the 8 MB threshold that would have split the file.

**B — `@cdktn/aws-migrate`** (`tools/migrate`, ts-morph). A dry run by default, printing a unified
diff and a report; `--write` applies it; the exit code is non-zero while anything is unmapped.

**C — the worked example**, `examples/migrate/typescript/`, golden-tested by
`pnpm migrate:verify` and by a new light CI job.

## The two decisions that shaped the tool

**The map is the only input.** No rule in `tools/migrate` restates a naming decision. A nested
type's four wrapper classes and two mapper functions cost no code: the suffix list comes out of the
map's own `nestedSuffixRules`, and one row expands into up to sixteen lookup keys. A classic export
with no row is reported and left alone — the import it comes through is kept, reduced to just the
symbols that could not move, so the file still compiles against both libraries while a human
decides.

**Occurrences resolve through symbols, never text.** Every rewritten occurrence is a reference the
TypeScript language service resolved back to a binding the file imported from
`@cdktn/provider-aws`. That is what makes a shadowing local `const S3Bucket = …`, a property named
`s3Bucket`, and a same-named import from another package all safe from it — and it is why type
positions need no second code path. `typeof`, generics, `satisfies`, `extends` and plain
annotations are references like any other.

Design room the spec left, and what was chosen:

| decision | why |
| --- | --- |
| `import * as aws from '@cdktn/provider-aws'` keeps its shape; only the package moves | `aws.s3.TfBucket` is a perfectly good call site, and retargeting one string beats rewriting a file's every reference |
| everything else merges into one sorted `import { … } from '@cdktn/aws'` | one import per file is the shape the new library is for |
| aliasing is `<group>`, then `<group>_`, then `<group>_2`, `<group>_3` | deterministic, and readable at the call site |
| a residual classic import carries only the unmapped symbols | maximises what moves without ever guessing at what did not |
| `mapperPrefix` present only when it differs from `className` | 2,396 rows stay free of a column that says nothing |
| the barrel shim is generated by the verify script, not committed | it is derived from `generated/`, and committing it would be a second thing to keep in step |

## The golden mechanism

The proof has two halves, and both run in CI on an `ubuntu-latest` runner:

1. **The tool still produces the committed output.** `classic/` is copied to a temp directory, the
   tool runs over the copy with `--write`, and the result is compared to `migrated/` byte for byte.
   `migrated/` is therefore a golden file for the tool itself: a change to the rewrite, or to
   `naming-map.json`, arrives as a diff a reviewer reads. `pnpm migrate:example` regenerates it; it
   is never hand-edited.

2. **The migration preserved the terraform.** `migrated/` is compiled and synthesised against this
   tree's generated packages and compared to `golden/cdk.tf.json`, the synth of the **classic**
   project against the real published `@cdktn/provider-aws`.

The classic library is ~460 MB installed — one npm package per resource — so half of step 2 cannot
run on a pull request. It runs locally instead: `pnpm migrate:golden:refresh`
(`scripts/migrate-golden.mjs`) installs it in a scratch directory outside the repository, synthesises
the classic project once, and commits the result plus a `golden/VERSION` recording the exact build.
The version is chosen by provider pin, not by recency: `@cdktn/provider-aws@25.3.0` declares
`cdktn.provider.version` 6.62.0, the same pin as `schemas/PROVIDER_VERSION`, and the refresh script
**fails** if the installed classic build disagrees with that file.

Step 2's own side never builds the monolith. It compiles the six groups the example imports with
`scripts/build-generated.mjs` (5.7 s) and resolves `@cdktn/aws` to a six-line barrel shim whose
`index.js`/`index.d.ts` re-export `generated/<group>/lib` under the group name — the same
`export * as <group>` submodule surface `scripts/build-monolith.mjs` publishes, minus the copy-in.
So the example is type-checked and synthesised against exactly the shape a consumer installs.

**Masked fields: two, and no others.** `//.metadata.version` (the cdktn runtime that synthesised the
file) and `terraform.required_providers.aws.version` (the provider version each library was
generated from). Both are properties of the build rather than of the bindings; the second is masked
because a provider bump lands here before the classic library republishes, and that skew says
nothing about the rename. `scripts/migrate-verify.mjs` prints both values on every run — today they
are `0.24.0`/`0.24.0` and `6.62.0`/`6.62.0`, so the two files are in fact byte-identical.

## What is NOT done

* **Publishing.** `@cdktn/aws-migrate` is `private: true` and no workflow packs it. `npx
  @cdktn/aws-migrate` is what the docs promise and what the first release has to make true; until
  then the tool runs from a checkout (`pnpm migrate ts --project …`).
* **The required-check set.** `migration tool and worked example` is the sixth non-matrix job name
  and is deliberately absent from cdktn-repository-manager's required contexts — a required context
  the manager does not know about makes a repository unmergeable. It goes in with the manager change.
* **Go and Python.** The map already carries both classic identities per entry; the tools do not
  exist. `docs/migrating-from-provider-aws.md` states the target spellings and says they are planned.
* **JSDoc `@type` annotations** are neither rewritten nor reported — they are comments, and the tool
  does not read them. The migration guide says to grep for `@cdktn/provider-aws` afterwards.

## Round 1 review fixes

Three defects an adversarial review found, all of them the same shape — the tool being *silent*
about something it had not decided:

* **`export { B }` where `B` is a classic import** was rewritten to `export { s3.TfBucket };`, which
  does not parse. An export clause takes names, not qualified names. It now joins the shorthand
  property assignment as a reported position (`rewrite.ts#resolve`).
* **`declaredNames` read the imported name of an import specifier**, so
  `import { readFileSync as s3 }` never marked `s3` as taken and the group barrel collided with it.
  It reads the local name now — the only one that is bound.
* **Import forms the tool does not model were passed over in silence** — `export … from`,
  `export *`, `import x = require(…)`, `import('…')`, and the `index-structs/` subpath where the
  large modules declare their structs. `package.json` had already dropped the classic dependency, so
  a green run could leave a project importing a package it no longer depends on. There is now a
  backstop that cannot be outgrown: after the edits, every classic specifier still in a
  module-specifier position that this run did not decide about is reported, and the exit code says
  so. `index-structs` is resolved properly (the module's index re-exports it), and a named import or
  namespace binding whose submodule has no map row is kept and reported rather than dropped.

Two cheaper follow-ons in the same pass: `package.json` keeps `@cdktn/provider-aws` beside
`@cdktn/aws` while anything is unmapped (a residual import still has to install), and
`migrate-verify`'s `includes("0 unmapped")` — which "10 unmapped" also satisfies — is anchored.
8 new tests, 35 in the tool's suite. Deferred: emitting `import type` when every merged binding came
from a type-only import; the behaviour is documented in the guide's limits table instead.

## Round 2 review fixes

Two more of the same shape, both on the paths round 1 opened:

* **A default import of the classic package was dropped, or retargeted.** `classicBindings` read
  the namespace and named bindings but never `getDefaultImport()`, so a sibling binding on the same
  statement marked it handled and the round-1 backstop skipped it: `import d, { iamRole } from '…'`
  lost `d` at exit 0, and `import d, * as ns from '…'` moved `d` onto `@cdktn/aws`, which has no
  member it could reach. The default binding is a reported binding now, `residualImport` spells the
  default slot back, and a statement that keeps ANY binding is never retargeted.
* **A name kept in a residual import had been freed for the group barrel**, because the alias search
  ran over every binding before knowing which ones the run would remove. `migrateFile` decides all
  of them first and only then assigns aliases, over the names actually removed.

3 new tests, 38 in the tool's suite. The evidence table's test row above is corrected to match.
Also softened: the guide's limits table claimed every limit was reported — three are silent
(JSDoc `@type`, `require(someVariable)`, `import type`), and they now say so.
